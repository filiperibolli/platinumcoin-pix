### 2.3 — as seis regras, provadas no repo inteiro

1. **Conta debitada vem do JWT.** `SendPixRequest` tem exatamente três campos
   (`services/payment-service/…/api/SendPixRequest.java:7-11`) e nenhum nomeia conta;
   `PaymentController.java:55` passa `user.accountId()`. Todos os 6 endpoints de payment-service usam

3. **Nunca saldo negativo, e a guarda está DENTRO do write.**

4. **Débito e crédito atômicos.** Um único `transactWriteItems` (`DynamoLedgerRepository.java:196`)

5. **Append-only.** Zero `deleteItem`/`UpdateItem` sobre `ENTRY#` em todo o repo. Os únicos

**A1 — Nenhuma chave Pix é semeada, então o primeiro comando de dinheiro do README falha na hora zero.**

`infra/localstack/init/01-dynamodb-accounts.sh` cria a tabela `pix_keys`;
`04-seed-accounts.sh` semeia **só as contas** (`put_account u-alice acc-001` / `u-bob acc-002`,
linhas 47-48). Nenhum script de init insere uma chave. Numa stack recém-criada:

```
$ aws --endpoint-url=http://localhost:8000 dynamodb scan --table-name pix_keys --query Count
0

# README.md:306-313, verbatim
$ curl -s -X POST localhost:8084/v1/payments/pix -H "Authorization: Bearer $TOKEN" \
    -H "Idempotency-Key: $(uuidgen)" -H 'Content-Type: application/json' \
    -d '{"pixKey":"bob@platinum.com","amount":"125.50","description":"lunch"}'
{"status":422,"detail":"The destination Pix key could not be resolved to an account.",
 "code":"KEY_NOT_FOUND",…}   ← README promete "202 Accepted { status: PROCESSING }"
```

O mesmo derruba `docs/local-dev.md` §5.3 (`:1027`) e §5.2 caso 1 (**B3**). As harnesses automáticas
não sofrem porque se auto-provisionam (o E2E registra a chave no ACT 2, a pasta *Flows* do Postman
idem) — só os documentos que um humano lê é que não. O `PLAN.md:182` registra que **exatamente este
defeito** foi encontrado no api-explorer no step 49 ("nothing registered the payee") e corrigido lá; a
correção nunca chegou ao README nem ao runbook.

*Conserto aplicado — e **não** foi semear.* `04-seed-accounts.sh` registra explicitamente a decisão
de não semear chave nenhuma ("*those are registered via the account-service API in step 10, exercising
the conditional-put uniqueness path*"), o que esta auditoria não tinha citado. A decisão é boa e ficou
intacta; o que estava errado eram os documentos, que assumiam uma chave que ninguém cria. O README
agora loga os dois usuários e registra a chave antes de enviar, e §5.2 registra as duas chaves nomeadas
de que o resto do §5 depende. Vale notar o que as harnesses escondiam: a jornada E2E e a coleção
Postman se auto-provisionam, então só os caminhos que um **humano** percorre estavam quebrados.

**A2 — A coleção Postman falha em qualquer sandbox que já recebeu um Pix, e a mensagem manda o leitor
caçar um bug de reversão que não existe.**

`newman run` numa stack em uso: **92 requests, 243 asserções, 1 falha, exit 1**.

```
AssertionError  no shard is negative at rest
  a negative shard means a reversal hit the wrong sub-account:
  expected [ 'SPI_CLEARING#01', …(4) ] to deeply equal []
  inside "ledger-service / Clearing position — the sum of the write shards"
```

A asserção (`tools/postman/pix-platform.postman_collection.json`, script de
*Clearing position — the sum of the write shards*) trata "shard negativo" como sinônimo de bug de
reversão. Mas um **Pix recebido debita um shard de clearing e credita o cliente**:

```
POST /internal/ledger/postings | txId=in-E99999999… debitAccount=SPI_CLEARING#13
  creditAccount=acc-002 amountCents=30000 entryType=PIX_IN
```

e a posição fica negativa até que uma saída caia no mesmo shard. Ao vivo: 6 shards em exatamente
`-30000` cada = os 6 Pix recebidos de R$300,00 da sessão. Isso é **o comportamento que o próprio
design documenta** — `ARCHITECTURE.md:724` e o javadoc de `AccountPolicy` dizem que a posição
interbancária é legitimamente negativa num dia de entradas.

Consequência: `docs/local-dev.md:1740` afirma que a coleção "runs top to bottom, repeatably, on a
stack in any state". Não roda.

*Conserto:* trocar a asserção universal por uma verificação de netting sobre os shards que a própria
execução tocou (a coleção já captura os txIds), ou reduzi-la a "nenhuma **conta de usuário** negativa".

**A3 — `scripts/e2e-journey.sh` reprova o próprio gate por um `grep -q` sob `pipefail`; as 3 falhas
observadas são um único bug em cascata.**

`scripts/e2e-journey.sh:43` liga `set -euo pipefail`. Em `:737-739`:

```bash
alerts_since() { docker compose -f "$COMPOSE_FILE" logs --no-color --since "…s" settlement-service 2>/dev/null; }
alert_fired()  { alerts_since "$DRILL_STARTED" | grep -q 'ALERT FIRING'; }
```

`grep -q` sai no primeiro match; se o produtor ainda está escrevendo, `docker compose logs` morre de
SIGPIPE e devolve 255, e o `pipefail` transforma um match em falha:

```
$ docker compose … logs --no-color --since 900s settlement-service | grep -q 'ALERT FIRING'
PIPESTATUS=255 0        ← e há 3 matches no stream
# 20 de 20 execuções reportaram "não encontrado"
```

O alerta **de fato disparou** na execução que falhou — duas vezes:

```
18:23:40 WARN AlertEvaluator: ALERT FIRING … rule=settlement_silence   observed=165.0
18:25:43 WARN AlertEvaluator: ALERT FIRING … rule=settlement_dlq_depth observed=1.0
```

A cascata: o predicado falso queima os 120s inteiros de `ALERT_WAIT_SECONDS`; somados aos 223s até o
DLQ isso passa dos `SLO_SECONDS=300`, então `REMAINING` em `:770-771` é **clampado em 5s** e a
asserção KR3.1 não tem como passar; e como a transação ainda não liquidou, o cheque de clearing
(`-30000` esperado, `-22000` observado) cai junto. A própria transação liquidou normalmente às
18:27:25, e o ACT 9 (`no outbound payment is left parked in clearing`) passou logo depois — a
plataforma estava certa, o harness não.

`alert_resolved` passa porque as linhas `ALERT RESOLVED` ficam **no fim** do stream, quando o produtor
já terminou — o que explica por que a mesma função acerta metade das vezes.

É intermitente, não determinístico: 1 FAIL e 1 PASS em 2 execuções. Mas o gate está no caminho
crítico da afirmação mais forte do repo (`tests/e2e/README.md:12` lista KR3.1 como provado pelo
DRILL A), o CI nunca o roda, e não há registro de execução repetida em lugar nenhum.

*Conserto:* capturar a saída numa variável antes de casar
(`logs=$(alerts_since "$X"); [[ "$logs" == *"ALERT FIRING"* ]]`) — remove o pipe e o SIGPIPE junto.

> Efeito colateral que vale registrar mesmo depois do conserto: a margem medida do KR3.1 nesta máquina
> foi de **31s em 300s**, e o DLQ levou 205-223s onde o doc estima ~135s (**D3**). O drill está no
> fio da navalha.

**A4 — A resposta à Pergunta 7 de design descreve um mecanismo que não existe.**

`ARCHITECTURE.md:1103`, dentro de "Ledger down for 30 seconds" — o parágrafo que responde à pergunta 7:

> `POST /payments/pix` during the outage: the ledger call fails fast (**timeout 1s, circuit breaker
> opens after N failures**) → `503 Service Unavailable` + `Retry-After: 5`

No código não há circuit breaker algum (`grep -i circuitbreaker\|resilience4j` só acha comentários
dizendo "*a deployed build adds* a circuit breaker", `HttpLedgerClient.java:79` e
`payment-service/src/main/resources/application.yml:180`), e o timeout é
`connect 2000ms + read 3000ms` (`application.yml:181-182`), não 1s. O bloco anterior da mesma seção
carrega o disclaimer "*production posture, documented; locally single-instance*"; este não — ele lê
como descrição do comportamento atual, e é o parágrafo que um entrevistador vai ler primeiro.

*Conserto:* marcar o circuit breaker como postura de produção e corrigir o número do timeout para
`2s conectar + 3s ler`.

`docs/security-checklist.md:126`, justificando por que o item 4 do §6 (validação roda antes da

**a razão escrita está errada** — e é a única razão escrita.

*Conserto:* reescrever a justificativa sem apoiar-se na publicação do schema, ou publicar o schema.

### 3.3 O que o projeto afirma e não prova

O repo já declara honestamente vários limites (a perna DynamoDB do benchmark, o ramo multipart do
export, Object Lock só na API do LocalStack, IAM que o LocalStack não aplica, PII em log). Os que
**ainda não estão marcados**:

1. **"Every service stateless → ≥3 replicas across 3 AZs"** (`ARCHITECTURE.md:1097`). Não existe
   eleição de líder, `@SchedulerLock` nem ShedLock em lugar nenhum. Com N>1 réplicas rodariam N
   scanners de transação presa, N archivers, N avaliadores de alerta (N páginas por incidente) e N
   publishers de outbox. Vários desses são idempotentes por construção — mas isso não está escrito, e
   o único lugar do repo que discute multi-réplica é o `SseEmitterRegistry` (que é honesto:
   *"a second replica would only reach the customers connected to it"*). **A afirmação mais larga do
   documento de arquitetura é a menos qualificada.**
2. **KR3.1 ("<5 min de reconciliação") na prática.** É afirmado como observado em `README.md`,
   `tests/e2e/README.md:12` e no `PLAN.md`. O único artefato que o mede reprovou em 1 de 2 execuções
   (**A3**) e passou com 31s de folga na outra. A afirmação está certa; a **prova** é frágil, e nada
   registra isso.
3. **"a p99 < 150ms" da fraud-service** (`ARCHITECTURE.md:1108`). O `load/RESULTS.md` mede 10ms sob
   carga — a afirmação está folgada, mas o número documentado é um *target*, nunca uma medição
   declarada como tal.
4. **A configuração medida como falha continua sendo a configuração enviada.** O repo mediu 8,4% de
   perda de sends na taxa média (58 TPS) e atribuiu a causa; nada mudou e nada entrou no roadmap
   (**C5**). Afirmar "sized to those numbers" no README (`:24`) enquanto a medição própria diz o
   contrário na taxa média é a afirmação mais cara desta lista.
5. **"Postman roda repetidamente em qualquer estado da stack"** (`docs/local-dev.md:1740`) — refutado
   por **A2**.

### 3.4 As três perguntas mais constrangedoras de uma entrevista

**1. "Rodei seus scripts. O `mvn verify` passou, mas o seu gate ponta a ponta reprovou 3 de 51
asserções e a coleção Postman saiu com código 1. Como eu diferencio, às 3 da manhã, um harness
instável de um bug de dinheiro?"**
*Tem resposta parcial.* A plataforma tem exatamente as ferramentas certas para essa pergunta —
Σ balances lido de forma independente pelo SDK em `E2EJourneyIT`, `scripts/trace.sh`, a camada INFO
que conta a história inteira. O que **não** tem resposta é o meta-nível: o gate nunca roda no CI,
não há registro de execuções repetidas, não há orçamento de flake, e as duas falhas que encontrei
estavam no harness — ou seja, a primeira vez que alguém rodou isso duas vezes seguidas foi hoje.

**2. "Sua arquitetura diz que todo serviço é stateless e roda com três réplicas. Se eu subir dois
payment-services agora, o que quebra?"**
*Tem resposta boa para metade e nenhuma para a outra.* O caminho síncrono aguenta: identidade durável
(ADR-0014), fencing settle-XOR-reverse (ADR-0016), dedupe por `eventId` no consumidor. O caminho de
background não está analisado em lugar nenhum: sem eleição de líder, dois scanners de transação presa
e dois avaliadores de alerta rodam em paralelo. A resposta provavelmente é "é seguro por
idempotência" — mas ela não está escrita, e a pergunta é a primeira que um staff faz depois de ler §7.4.

**3. "Você mediu 8,4% dos sends falhando na sua própria taxa média, achou a causa — seu pool de
conexões — e não consertou nem colocou no backlog. Por quê?"**
*Tem meia resposta, e ela é boa.* `load/RESULTS.md` §5 argumenta que dimensionar o pool é uma mudança
com trade-offs reais que merece o próprio step, e não deve ser contrabandeada dentro de uma medição —
o que é uma resposta de engenheiro sênior. O que não tem defesa é o item nunca ter chegado ao
`PLAN.md`. "Está escrito na página 12 do relatório de carga" e "está no roadmap" não são a mesma coisa
para quem está avaliando julgamento de prioridade.

### 3.5 O que falta para um sistema de pagamentos real e não está nomeado no backlog

Li os 8 itens do backlog antes; nada abaixo se repete com eles.

1. **MED — Mecanismo Especial de Devolução.** O brief exclui "automatic refunds", mas o MED não é
   estorno voluntário: é obrigação regulatória do BACEN para Pix sob suspeita de fraude, com prazos e
   um fluxo de notificação entre PSPs. O repo tem a peça mais difícil (posting compensatório
   append-only, step 33) e nenhuma menção ao mecanismo.
2. **DICT como registro nacional, não só como consulta.** `account-service` "plays the role of BACEN's
   DICT for internal keys" (`ARCHITECTURE.md:183`) e delega a consulta externa ao mock. O que um
   participante real precisa e não está nomeado: **publicar** suas chaves no DICT, e os fluxos de
   **reivindicação de posse e portabilidade** — que são justamente onde a "unicidade global" das
   chaves deixa de ser um `attribute_not_exists` local e vira um protocolo com outro PSP.
3. **PLD/FT e sanções.** `fraud-service` faz velocidade/valor/novidade/horário. Um sistema de
   pagamentos real precisa de screening de listas restritivas e de reporte ao COAF; são controles
   diferentes, com latências e consequências diferentes (o screening pode bloquear, o fraude
   fail-open não pode). O ADR-0005 discute o trade-off de disponibilidade sem nunca separar as duas
   naturezas de controle.
4. **A ferramenta do operador que o próprio design pressupõe.** `409 OPERATION_UNRESOLVED` é
   deliberadamente devolvido **sem `Retry-After`** porque "*it will not resolve on its own and needs an
   operator*" (`openapi.yaml:157`), e o drill de DLQ existe porque "*a human should see it before it is
   replayed*". Não existe nenhuma superfície para esse humano: nem endpoint, nem console, nem runbook
   de resolução manual. O desenho nomeia um ator que o sistema não tem.
5. **Retenção × direito ao esquecimento.** O trilho de auditoria é Object Lock COMPLIANCE por 5 anos
   (imutável por construção) e o ADR-0012 registra a postura de LGPD para *logs*. A tensão entre a
   retenção obrigatória de 5 anos e o direito de eliminação da LGPD sobre os dados pessoais dentro
   desses objetos não é nomeada em lugar nenhum.
6. **Eleição de líder / lock distribuído para os jobs agendados** — ver 3.4 pergunta 2.
